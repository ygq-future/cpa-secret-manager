# 0006: 用量按小时时间桶归因，并受数据保留天数约束

## Context

ADR-0002 决策 3 选择"只保存累计计数、不做时间窗口"。随之而来的是页面的日期范围按钮无法作用于密钥页：统计卡、每行请求数/失败数/Token、模型明细全部读累计值，切换范围后数字纹丝不动；只有失败记录（`errorslog`，每条带时间戳）会跟着范围变化。界面在暗示一个数据模型并不具备的能力。

要回答"某区间内多少请求、多少 Token"，必须把时间归属存下来。可选做法有三类：

1. **逐请求明细**：体积 ∝ 请求条数，且每 5 秒全量重写状态文档的写入方式无法承受（`defaultFlushInterval`），需要改用追加写或引入 bbolt——ADR-0002 明确否决了嵌入式数据库。
2. **秒/分钟级聚合**：粒度越细，桶数量按倍数膨胀。
3. **小时级聚合**：每天 24 个桶，按"密钥 × 模型 × 小时"计，且只为实际出现过的组合建桶。

同时，保留天数（`retention_days`，1–365，默认 30）此前只作用于失败记录：设置页却写着"所有数据…超时记录将自动清理"，对用量并不成立。

## Decision

1. 用量按 **UTC 整点小时桶** 聚合：`usage.Aggregator` 以 `SHA-256(APIKey)` → `2026-10-20T09` → `Bucket{Counters, Models}` 保存。桶是唯一带时间归属的用量数据。
2. 状态文档 `schema_version` 升到 2：旧文件里的 `usage` 段被忽略。桶文档 **独立落盘**：`<state_path 去扩展名>-buckets.json`（默认 `data/cpa-secret-manager-cache-buckets.json`），与 `cache.json`（设置、备注、配额规则）和 `-errors.json`（失败记录）并列。设置文件保持小而可读。
3. `resolve` 接受 `start` / `end`（RFC3339）。缺省边界回退到保留窗口；**请求超出保留期的部分被裁剪**，完全落在保留期外的区间返回空结果，绝不退化成"全量"。
4. 每次刷盘先按保留天数裁剪桶（`cutoff = now - retention_days`）再写入，窗口外的桶不会回写；失败记录沿用同一 `cutoff`。
5. 页面以下限 `now - (retention_days - 1) 天` 的零点、上限 `now` 约束日期选择器，超出范围的日期不可点选，并随设置变更实时收紧。

## Consequences

- 桶精度是**小时**：区间边界按小时取整，因此"今天"在整小时偏移的时区下是精确的；半小时偏移时区（如 +05:30）最多偏差 30 分钟。
- 升级后旧版 `cache.json` 里的累计计数不再被读取，历史总量无法按时间归属（旧数据没有时间维度）。时间数据从升级后开始累积，并随保留期滚动。
- 状态文档体积与"密钥 × 模型 × 小时"的**实际组合数**相关，而非请求总数：请求量增长不增加桶数量。
- 设置页的"数据保留天数"从此对用量桶与失败记录同时生效，文案与实现一致。
- ADR-0002 决策 3 中"不做时间窗口"的部分由本 ADR 取代；"不消费官方用量队列、不用嵌入式数据库、节流原子落盘"的结论不变。
