# 0009: 参考价按分段前缀匹配并展示全部报价

## Context

ADR-0007 的参考价只按完整模型名的别名（路径段、`@` 日期、日期/版本后缀）匹配，并选出一条代表报价。实际接入的渠道会给模型名追加能力或渠道标记，例如 antigravity 的 `gemini-3.5-flash-high`：目录中只有 `gemini-3.5-flash`，完整名匹配失败，页面因此显示"未找到参考价"。

同时，同一模型在 models.dev 上常有多个 provider 报价。只展示一条代表价时，用户无法核对或选择更贴近实际渠道的价格。

## Decision

1. **分段前缀逐级匹配**。模型名先归一化为最后路径段，去掉 provider 标签、vendor 点前缀与 `@` 日期；再按 `-` / `_` / 空格切段。对请求名依次尝试 `gemini` → `gemini-3.5` → `gemini-3.5-flash` → 完整名，前缀必须在段边界结束（`gemini-3.5-flash` 不匹配 `gemini-3.5-flashlight`）。
2. **最深命中层回退**。取所有候选中匹配层数最大的那一层；若完整名没有命中，就使用上一层的全部候选。`gemini-3.5-flash-high` 因此落在 `gemini-3.5-flash` 这一层。为避免只共享厂商族名的误匹配，多段模型名至少需要命中两段（`claude-3-5-haiku` 不会仅凭 `claude` 落到其他 Claude 型号）。
3. **层内排序**。同层候选按综合分排序：完整名命中、是请求名的截短形式、canonical 命中、官方 provider、非零价格、缓存价与更新时间分别加权；再以额外段数、更新时间、provider 与 model id 打破平局。第一条即"最合适"。
4. **返回全部报价**。`Suggestion` 增加 `offers` 数组（每个 `Offer` 含 provider、model、三项价格与更新时间），按上述顺序排列，单模型最多保留 50 条；`providers` 记录列表中的报价数。
5. **页面用下拉框选择**。参考价行改为下拉框：列出全部报价，默认选中"已采用"的报价（没有则选第一条最合适报价）；触发器显示价格、provider 与"已采用 / 同步时更新 / 同步时添加"状态。选择报价只填入三个单价输入框，保存仍是独立动作。
6. **缓存 schema 升级**。`prices.json` schema 升到 2；读取 schema 1 时用原有代表价合成单条 `offers`，下一次显式同步后自然变成完整列表。
7. **刷新与保存解耦**。顶部"仅同步"只刷新全部当前模型的缓存，不写 `model_prices`；参考价行末尾的刷新按钮以 `merge` 模式只刷新当前模型，保留其他模型的缓存项。两者都只在用户点击时联网。

## Consequences

- 带渠道后缀的模型名能落到基础型号；不同 provider 的报价可以在页面直接切换。
- 报价列表按模型名与 provider 排序后截断，缓存体积仍与"当前模型列表"成正比。
- 匹配仍只发生在显式同步/读取缓存时，不增加网络请求；打开设置页、切换模型都不会触网。
- 目录中完全不存在同族前缀时仍显示"未找到参考价"。

## Alternatives

- **模糊/编辑距离匹配**：容易把 `flash` 匹配到无关型号，且无法解释结果；放弃。
- **只去掉已知后缀列表（`-high`、`-low`）**：无法覆盖未知渠道标记；放弃。
- **保留单条代表价**：无法满足按 provider 核对与选择的需求；放弃。
